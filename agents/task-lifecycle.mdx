Every unit of work in Agent2Agent is represented as a **Task**. A task travels through a defined set of states from the moment a client sends its first message until the agent delivers a final result or the conversation is abandoned. Understanding this lifecycle — and how `contextId` and `taskId` keep multi-turn conversations coherent — is essential for building reliable agents and clients. This page explains every state, the valid transitions between them, and shows real JSON request/response sequences from the LangGraph currency agent sample.

## Task states

<CardGroup cols={2}>
  <Card title="submitted" icon="circle-dot">
    The task has been created and enqueued but the agent has not yet started processing. This is the initial state emitted when a new task object is first pushed to the event queue.
  </Card>
  <Card title="working" icon="spinner">
    The agent is actively processing the request. The agent may emit one or more intermediate status-update events in this state to give the client real-time progress.
  </Card>
  <Card title="input-required" icon="circle-question">
    The agent cannot proceed without additional information from the user. The task is paused and the client must send a follow-up message that references the same `contextId` and `taskId`.
  </Card>
  <Card title="completed" icon="circle-check">
    The agent has finished successfully. Artifact events containing the result will have been emitted before or alongside this terminal state transition.
  </Card>
  <Card title="failed" icon="circle-xmark">
    An unrecoverable error occurred. The task will not be resumed. Clients should inspect any error details in the status message.
  </Card>
  <Card title="canceled" icon="ban">
    The client issued a `tasks/cancel` request and the agent honoured it. This is a terminal state.
  </Card>
</CardGroup>

## State transition flow

A task always starts as `submitted` (or jumps directly to `working` if the agent doesn't publish the initial task object explicitly). From `working`, the three possible outcomes are `completed`, `failed`, or `input-required`. Only `input-required` is non-terminal: the client provides the missing information, which causes the task to re-enter `working`. Any state can transition to `canceled` if the client cancels before completion.

```text
submitted ──► working ──► completed
                │
                ├──────► failed
                │
                └──────► input-required ──► working (resumed)
                               │
                               └──────► canceled
```

<Note>
  `completed`, `failed`, and `canceled` are terminal states. Once a task reaches one of them, no further events for that task will be emitted.
</Note>

## contextId vs taskId

These two identifiers serve different scopes:

| Identifier | Scope | Purpose |
|---|---|---|
| `taskId` | A single processing unit | Uniquely identifies one invocation of the agent. Changes if a task is recreated (e.g., after cancellation). |
| `contextId` | An entire conversation thread | Ties multiple tasks and messages belonging to the same logical session. Preserved across `input-required` / follow-up turns. |

When a client sends the very first message in a conversation, neither `contextId` nor `taskId` are included — the server generates both. For every subsequent turn, the client **must** echo back the `contextId` and `taskId` it received, so the agent can restore memory and continue the prior thread.

## Single-turn example

A simple request that completes in one round-trip — the agent has all the information it needs.

    "method": "message/send",
    "params": {
        "message": {
            "kind": "message",
            "messageId": "120ec73f93024993becf954d03a672bc",

                {
                    "kind": "text",

}

## Emitting input-required from an executor

In your `AgentExecutor`, signal that the agent needs more information by calling `update_status` with `TaskState.input_required` and `final=True`. The `final=True` flag tells the SDK this is the last event for this processing cycle.

```python
await updater.update_status(
    TaskState.input_required,
    new_agent_text_message(
        'Please specify which currency you would like to convert to.',
        task.context_id,
        task.id,
    ),
    final=True,
)
```

<Warning>
  Always pass `final=True` when transitioning to `input-required`, `completed`, `failed`, or `canceled`. Omitting it on a terminal transition will leave the SDK waiting for more events that will never arrive, causing timeouts on the client side.
</Warning>

## Task history

Every response includes a `history` array listing all messages in the conversation in chronological order. Each message carries both `contextId` and `taskId` so the full lineage is traceable. The history grows across `input-required` / follow-up cycles within the same `contextId`.
